# desktop-native-integration Specification

## Purpose
Let people save exports, dictate into chat and notice agent activity while preserving the boundary between a remote MauzCode server and the user's computer.

## Requirements

### Requirement: Save a user-requested download
The client SHALL offer a native Save As dialog for a user-requested file or export from the active server. It SHALL respect the chosen destination and cancellation, and MUST NOT automatically open or execute the file.

#### Scenario: Save or cancel an export
- **WHEN** a signed-in user requests an export, including one generated by the active web page
- **THEN** the user selects the destination or cancels; only the selected file is saved on success, nothing is saved on cancellation, and nothing is launched.

#### Scenario: Unrelated source
- **WHEN** an embedded third-party page, another origin after redirect, or an inactive server attempts a download
- **THEN** the client denies the request and does not write a file.

### Requirement: Grant and revoke microphone access
The client SHALL let the user explicitly grant audio-only microphone access for existing web dictation on trusted HTTPS or localhost, subject to OS consent. The grant SHALL apply only to the selected origin, be revocable, and MUST NOT grant camera access.

#### Scenario: Start dictation
- **WHEN** the user activates dictation on a supported origin for the first time
- **THEN** capture requires consent, subsequent dictation follows the server's normal workflow, and declining leaves typing available.

#### Scenario: Revoke or switch servers
- **WHEN** the user revokes the grant during capture or switches away from the capturing server
- **THEN** capture stops, and the new server cannot use the old grant; after revocation a new capture requires fresh consent.

#### Scenario: Insecure LAN or unsupported permission
- **WHEN** the selected non-loopback origin uses HTTP, or content requests a camera or an unrelated permission
- **THEN** the client denies access; for dictation on LAN HTTP it explains the HTTPS or localhost requirement without blocking normal chat.

### Requirement: Background notifications for the signed-in user
The client SHALL offer opt-in system notifications for finished agent runs and requests awaiting human input while the app is minimized or in the tray. Notifications MUST originate from events authorized for the active user and server. They SHALL open the associated chat and MUST NOT be duplicated by reconnect or replay.

#### Scenario: Agent waits or finishes in the background
- **WHEN** the user has opted in, the app is in the background, and an authorized pending-input or run-completed event arrives
- **THEN** the app shows one OS notification for that occurrence; selecting it restores the window and opens that chat using normal server authorization.

#### Scenario: Replay or stale identity
- **WHEN** the client receives a repeated occurrence, or the user has opted out, signed out or switched servers before a notification is delivered or activated
- **THEN** it does not display a duplicate or disclose or navigate to another identity's chat.

#### Scenario: Unavailable events
- **WHEN** the connected server does not support either notification event, or OS notifications are unavailable
- **THEN** normal sign-in and chat continue and settings explain the limitation; the pilot does not promise delivery after explicit Quit.

### Requirement: Preserve the remote-content boundary
Remote pages SHALL remain sandboxed without Node access, filesystem APIs or general-purpose desktop IPC. Capability decisions SHALL be scoped to the active top-level server origin rather than inherited by child frames or other servers.

#### Scenario: A foreign frame requests native access
- **WHEN** a nested or foreign frame asks for a desktop permission or tries to invoke a local settings action
- **THEN** it receives no grant or privileged result, even when the top-level server has a microphone grant.
