# Design

## Context

Model availability today has two levels: a connection `enabled` flag and per-connection `disabled_models`. Both are enforced centrally by `models.inference.assertModelEnabled`, which every inference entry point (`stream`, `compact`, `call`, `countTokens`) and `resolveRoute` already call before any provider code runs, reading stored state on every request. The frontend receives one shared catalogue (`frontendBridge.modelCatalogue`) and one selection policy (`selectableModels` in `frontend/src/lib/models.ts`) that hides disabled models and models of disabled connections from every picker. Providers are declarative `$modelProvider_*.ts` files (code, not state); `models.providers()` projects them as a synchronous secret-free `ProviderView[]` catalogue consumed by the Models settings API and several frontendBridge projections. Settings are declared per module (`$setting_<key>.ts`) with global JSON values supported (`docs/settings.md`); no migration is needed for a new setting.

## Goals / Non-Goals

**Goals:** one global owner switch per provider; immediate enforcement on the next request of any existing session; models gone from every picker; connections and secrets preserved; state visible through the existing provider catalogue; zero per-provider implementation burden.

**Non-Goals:** per-user or per-agent disablement; provider-declared self-disable hooks; deleting or mutating connections; changing the provider SDK declaration contract; a default-provider setting.

## Decisions

- **Central enforcement, not SDK self-disable.** Letting each provider check its own flag would duplicate the gate in every provider (including third-party plugins) and a provider that forgets the check would silently break the guarantee. One internal guard `models.inference.assertProviderEnabled({ provider })` throws `PROVIDER_DISABLED`; it is called by `assertModelEnabled` (covering `stream`, `compact`, `call`, `countTokens`) and by every other path that can reach the provider over the network.
- **Every network path is gated in the backend, not only in the UI.** Besides inference, the guard (or an equivalent short-circuit) runs in: `resolveRoute` — immediately after `parseRoute` and before `connections.resolve`, to establish error precedence before connection lookup and prevent entry into provider code; the current `connections.resolve` only assembles lazy secret/fetch access and does not itself refresh OAuth tokens; `connections.action` — before `connections.resolve`, failing `PROVIDER_DISABLED` (409) so a direct POST cannot run Login/Logout flows; `catalog.listModels` — a disabled provider is treated like a disabled connection and always returns the cached/manual fallback, so the `models` action with refresh never calls discovery; `connections.test` / `connections.usage` — return status `disabled`; `catalog.refreshAll` — skips the provider. UI blocking is presentation only.
- **State in one declared setting.** `models.disabledProviders` (`type: "json"`, default `[]`, validate: array of non-empty strings) at global scope. A dedicated reader `models.disabledProviders()` normalizes to a `Set<string>` and reads on every call without caching, mirroring the gate's read-through behavior so a toggle takes effect on the very next request. Batch projections (`modelCatalogue`, `modelUsage`, `refreshAll`, `modelDefault`) read it once per request and test membership per connection. No new table or column.
- **Unknown ids are kept, not rejected.** Validation checks shape only (array of non-empty strings), never registration: a plugin provider may be unloaded or not yet loaded when the setting is read or written by a settings file. Ids of unregistered providers are stored and ignored; if the plugin returns, it comes back disabled. The API action alone requires a registered id.
- **File-fixed setting.** An instance settings file may fix `models.disabledProviders`; `settings.set` then throws. Extend the existing fixed-setting error in `settings.set` with a stable `code: "SETTING_FIXED"` and structured file-path metadata, preserving its message. The API maps this code (never message text or unrelated storage errors) to 409 `SETTING_FIXED` with the file path, and the provider view carries `enabledLocked: true` so the UI renders the switch disabled with a hint instead of a failing toggle.
- **Serialized writes.** `setProviderEnabled` does read-modify-write; two concurrent toggles of different providers would lose one. The action runs inside a promise chain owned by `ctx.state.models` (single-process mutex, no module-level mutable state) so writes are serialized; the write is idempotent per provider. Return each operation's original promise to its caller, but recover the stored queue tail after rejection so a failed write cannot poison subsequent toggles.
- **`models.providers()` stays synchronous; `enabled` is added at the API projection.** The declaration catalogue describes code, not state, and most callers (`providerIcons`, `modelMark`, `modelUsage`, `modelCatalogue`, tests) never need enablement. Making it async would touch ~10 call sites and fixtures for no benefit, and would not improve freshness: the read-through guarantee belongs to `models.disabledProviders()`, which every enforcement point calls directly. The `/models/api` GET and `providers` action return `ProviderSettingsView = ProviderView & { enabled: boolean; enabledLocked: boolean }`, computed per request. The declaration contract (`ProviderDefinition`) is untouched.
- **New failure code `PROVIDER_DISABLED`.** Distinct from `CONNECTION_DISABLED` so the message names the provider, not an account the owner never disabled. Shape matches the existing disabled failures: status 409, `retryable: false`, `replaySafe: false`, thrown before any network request; added to `agent.retryCodes().never`. `resolveRoute` checks the parsed provider first and maps it through its existing non-retryable failure path so `agent.setModel` and agent turns get a clean invalid-input failure. Precedence: `PROVIDER_DISABLED` before `CONNECTION_NOT_FOUND`, `CONNECTION_DISABLED` and `MODEL_DISABLED_BY_USER`.
- **Catalogue projection reuses the disabled-connection semantics.** For a connection of a disabled provider, `modelCatalogue` reports the group `enabled: false, unavailable: false` (not an unavailable-catalogue notice) and its models `disabled: true`; it reads only cached/manual models and never asks the provider. The frontend `selectableModels` policy already hides exactly this shape, so no picker code changes.
- **Writes through the existing owner API.** New POST action `setProviderEnabled { provider, enabled }` on `/models/api` behind the existing owner/CSRF/JSON/body-limit checks; validates a registered provider id, read-modify-writes the setting via `settings.set`, returns the updated state. `create` rejects disabled providers (409 `PROVIDER_DISABLED`) so no knowingly-dead connections appear; `list`/`update`/`remove`/connection toggle remain available; `test`/`usage` short-circuit to status `disabled`; `action` and refreshing `models` are refused or served from cache as above. The `frontendBridge.modelUsage` projection omits connections of disabled providers entirely, like disabled connections, so quota widgets show no dead rows.
- **UI grouping.** The Models panel groups the flat connection list under provider headers (logo, label, switch; providers without connections get a header too). Disabled providers: badge, dimmed cards, Test/Update models/Login blocked (same treatment as a disabled connection); the connection-level switch stays operable. AddConnection hides disabled providers from the selector, with a note when all are disabled. Toggle uses the existing `actions.run` + reload flow. Follows the Apple Design skill: existing tokens and switch pattern (`models-enabled`), light/dark, accessible role/name, no new dependencies.

- **Disablement boundary.** The successful setting write is the toggle's completion boundary. Operations whose availability check reads the setting after that write must be blocked before provider invocation. An operation that already passed its check may finish, even if provider invocation or network activity begins after the toggle; existing streams are not cancelled. This is an admission check, not atomic cancellation of in-flight work. A subsequent inference request must perform a fresh check; batch projections use their documented per-request snapshot.

## Risks / Trade-offs

- Every new network path added later (a new provider action, a new discovery entry point) must call `assertProviderEnabled`; mitigated by keeping the guard next to `connections.resolve` call sites and by acceptance tests that both stub `fetch` to fail on any request and instrument provider methods to assert zero invocations for operations checked after disablement.
- The write mutex is per process; a multi-process deployment could still race. Acceptable: the runtime runs one server process, and the loss is limited to one toggle that the UI shows after reload.
- A session mid-run fails on its next request when the provider is toggled off — this is the requested behavior; the error is explicit and non-retryable, and re-enabling restores the session without touching its stored model.
- The setting is instance-global; multi-user instances share the owner's decision. Per-user disablement is explicitly out of scope.

## Migration Plan

None. New declared setting with an empty default; existing behavior is unchanged until the owner toggles a provider. Rollback is deleting the setting row (or the declaration); connections were never modified.
