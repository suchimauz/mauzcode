# Design

## Context

See `proposal.md` for motivation. `LiveComposer` already hosts `TodoDock`, and `LifecycleRow` renders `wake_up` from the agent events API. `agent.deliverTriggerPrompt` persists the model-facing delivery and its display event together. `agent.processTrigger` distinguishes delivery from silent timeouts and retryable errors. The Meta snapshot is the newest 100 definitions of all statuses; `agent.triggers` can include raw configuration and results. Neither response is an appropriate panel payload.

The trigger POST handler already makes a trigger due by moving `next_at` and waking the worker. It does not tell the caller whether an active row actually changed. `commands.parse` and `commands.dispatch` have planning-specific defaults outside the compact branch; registering just a name would route `/trigger` into planning logic.

## Goals / Non-Goals

Keep three facts distinct: the human requested an action, the server accepted or rejected it, and the engine subsequently performed work. Reuse the scheduling, task-grant and delivery contracts. Do not build a second scheduler, parse natural-language times in the browser, turn the audit panel into a dependency, or backfill model or chat history.

## Decisions

1. **Read state from the engine, not the transcript.** Introduce an owner-authorized per-agent GET for active/checking definitions; filter before any pagination and expose only an ID, kind, status, bounded display purpose, next due/check time, and relevant cron expression/time zone. Order by next time, then stable ID. Derive groups from the same selection; do not count runs or filter a capped Meta response in the browser. The panel owns a separate disclosure from `TodoDock`. Use existing light/dark tokens, focus styles, labelled buttons and wrapping labels; when expanded, constrain list height instead of pushing the input off-screen.

2. **Live hints invalidate; reads reconcile.** Use the existing agent-scoped `ui.metaSection` transport (`wake`, `automation` or `all`); invalidate after committed changes, including a check rescheduling without delivery. Do not append transcript entries for these refreshes. Coalesce adjacent hints, abort reads and reset state on agent changes. On a same-agent read failure keep the last known data distinct from a confirmed empty list; refetch after reconnect. Reuse normal transcript stream and pagination rather than combining a second browser-side audit feed with it.

3. **One operation per intent across surfaces.** Retain the core create and single-cancel operations, including task reconciliation. Extract the conditional run-now update from the form route into a scoped operation callable by the route, authorized chat boundary and appropriately granted agent tool. Only an active row may become due; return one explicit outcome based on the actual write and current recipient state — `scheduled`, `deferred_paused` (made due while the recipient is paused; it runs after resume), `already_checking` or `not_active` — and wake the worker only after commit. The worker alone claims and evaluates it. Let its existing paused-recipient, cron, watch edge and delivery rules decide what happens next. Do not implement a button by invoking the predicate or injecting a prompt directly.

4. **Cancel the exact target, without a confirmation step.** Triggers are cheap to recreate, so cancellation from a row or from `/trigger` applies immediately through the existing single-cancel operation; no target-bound approval form is added. The row sends its own trigger ID; the conversational flow cancels only after resolving exactly one target of the current agent (ambiguity is clarified, zero matches is a no-op). Keep `cancelTrigger`, `cancelAllTriggers` and independent task cleanup unchanged. Recheck authorization, applicable capability, session eligibility, durable PLAN state and trigger status at mutation time, including after clarification. Use cookie-bound CSRF on UI writes. The server must not trust disabled buttons, a foreign ID or a user-supplied agent grant. Return a safe not-applied response for stale targets without disclosing another owner's data.

5. **Treat `/trigger` as a human request.** Add catalogue metadata and a discriminated command parse result with an explicit dispatch branch; keep `/plan` and `/compact` separate, including argument handling. In an eligible chat accept one normal-authority command turn (no attachments); preserve exact user arguments as data. A bare command asks for a type; a complete request selects the existing engine operation; ambiguous names resolve only against the current agent's authorized selection. Use the ordinary structured clarification path. Never interpolate arguments into system instructions, evaluate them, toggle planning or supersede a review. Existing session/queue policy still governs when a turn can run. An accepted command response means the request was received, not that a trigger exists or fired.

6. **Persist replay identity at the operation boundary.** Command submission keeps using the existing `agent_command_requests` record. Add an additive `agent_trigger_action_requests` table (`agent_id`, `request_id`, `action`, `trigger_id`, `result` JSONB, `created_at`; primary key `(agent_id, request_id)`), modelled on `commands.dispatch`. Row and conversational mutations look up the key first, then insert the record, apply the state transition and append the required event in one transaction. Same key with a different action/target is rejected with a conflict; an identical retry returns the stored result, not today's state, even after the worker has fired. A conversational mutation derives its key from the accepted command request and the resolved action so clarification does not create a second identity. Disabling a busy button alone cannot protect against a lost response.

7. **One lifecycle row per real transition.** Append display-only session events through session helpers in the same transaction as successful create, cancel (single, existing bulk and task cleanup paths), or expiry without a committed timeout delivery. Skip the creation entry when the trigger was created by a tool call already visible in the same chat; mark that tool card with a "trigger created" badge instead. Creation from the form, task cleanup or another agent still gets its own entry. Decide from the terminal state and delivery for this transition, not the presence of a timeout prompt: an edge watch can expire while its timeout prompt is coalesced with a pending firing. For delivered firings and delivered watch timeouts use the existing `wake_up` snapshot exclusively. Record the safe identifying fields at transition time; allowlist them in the authorized events API and render text, not HTML. Keep these notices visible in chronological history, not solely inside a collapsed work/tool block; do not create extra user/model messages. Current predicate errors always retry with backoff, so no terminal-failure entry is produced in this change: never show retryable errors in chat and never synthesize failures from attempt counts. The event contract may reserve a failure variant for a future engine terminal state, untested here. Publish refreshes after commit; reconcile live session state through existing helpers.

8. **Record the creator to avoid duplicate creation notices.** Add nullable `created_by_agent_id` and `created_by_tool_call_id` to `agent_triggers`. `wake`/`cron`/`watch` fill them from the calling session and the currently executing tool call; a call made inside a code-evaluation tool records the enclosing evaluation call. The creation entry is skipped only when the creator owns the trigger and the recorded tool call belongs to its chat; the events API exposes the trigger ID on that tool card so the UI can show a "trigger created" badge. If A creates a trigger for B, A's card gets the badge and B's chat gets one creation entry naming A. Form, task-cleanup and creations without a recorded call always produce an entry. Existing rows stay NULL; no backfill.

9. **Derive the purpose; do not store it.** The panel read and lifecycle snapshot compute purpose from the first non-empty prompt line, whitespace-collapsed and truncated to 120 characters with `…`. It is rendered as text. Raw predicate configuration is never part of it.

10. **CSRF on every trigger UI write.** New row actions use JSON `POST /agents/:id/triggers/:triggerId/actions` (`{requestId, action: 'run'|'cancel'}`) with an `x-csrf-token` header verified by `auth.verifyCsrf`, as in `commands/http.ts`. The existing inspector form route `$route_$id_triggers_POST.ts` gets the same check, and the inspector form sends the token; its `run` branch delegates to the shared make-due operation.

## Risks / Trade-offs

- **Concurrent cancellation and delivery** → lock/conditional-update the actual target; emit cancellation only for a changed row. A committed recurring firing may legitimately precede a successful cancellation of future runs.
- **Accidental disclosure via watch conditions, results or exceptions** → use a display allowlist and bounded purpose, not serialized predicate options, raw error dumps or audit records. Leave existing authorized audit/result access intact.
- **Noisy schedules and large lists** → group by kind, render details on expansion and coalesce refetch hints. Never truncate counts to the last 100 or turn intermediate polls into transcript entries.
- **Additional agency through a new command/tool** → classify the shared operation in preset/access review; deny disallowed operations server-side and never change the user's session mode as a side effect.

## Migration Plan

Ship additive request-receipt storage (or extend the existing receipt contract), operations and event projection before enabling chat controls. Old trigger definitions already provide the panel state; no history migration, synthetic events or delivery replay. On rollback, disable the new command and panel and stop producing the additive notices. Preserve receipts, old and new history, existing schedules and audit records; do not undo user-triggered actions.
