# Design

## Context

`LiveComposer` owns the draft, attachments, idempotent send and queue decision; `MessageInput` owns editor shortcuts and switches between `CommandEditor` and a plain `textarea`. `ComposerFooter` contains the context meter. The runtime already supports authenticated `$ws_<path>.ts` endpoints through `procs.http.upgrade` (origin check, per-connection state; see the Terminal plugin) and server-side secrets.

The existing Whisper plugin is **out of scope**: the new feature does not import, call or adapt it. The Models SDK is a design reference only; no Models code, table or facade entry is reused or modified.

### Reference: how openai/codex does it

Inspected `codex-rs/codex-api/src/endpoint/realtime_websocket` and `core/src/realtime_conversation.rs` (commit bd3eaf7):

- Realtime has two session modes, `Conversational` and `Transcription`. Transcription sends `session.update` with `type: "transcription"`, `audio.input.format = { type: "audio/pcm", rate: 24000 }`, `audio.input.transcription.model` and `turn_detection: null`; no instructions, tools, output modalities or voice.
- Audio is mono PCM16 at 24 kHz everywhere; frames are sent base64 in `input_audio_buffer.append`.
- Credentials and headers are applied only on the client side owned by Codex (`auth.apply_auth_headers`), never by UI code. The URL is normalized to `/v1/realtime`; the transcription intent is a query parameter.
- Incoming events are parsed per protocol version into a neutral `RealtimeEvent` enum (`InputTranscriptDelta`, `…Done`, `SpeechStarted`, errors). Transcript state is a list of entries: deltas append to the last entry, a final **replaces** the accumulated text; delayed finals can arrive after deltas of the next utterance and must not destroy accumulated text.
- Conversational voice in the TUI uses WebRTC plus a server "sideband" WebSocket joined by `call_id`. That is for speech-to-speech and is not needed for dictation.
- The app only flags accepted input with `used_dictation` metadata; dictation never auto-submits.

### Reference: OpenAI Realtime transcription API

From `developers.openai.com/api/docs/guides/realtime-transcription` and related pages:

- Server connection: `wss://api.openai.com/v1/realtime?intent=transcription`, header `Authorization: Bearer <key>`, **no `model` in the URL** (a model URL creates a conversation session and rejects a transcription update).
- First message `session.update` with `type: "transcription"`; wait for `session.updated` before streaming. The update can be resent mid-session to change context.
- Transcription options: `model` (`gpt-live-transcribe` recommended; `gpt-transcribe` for committed-turn + detected language), `prompt`, `keywords` (one line, no `<`, `>`, CR, LF), `languages` (ISO 639-1 / selected 639-3 / `zh-*`; `gpt-live-transcribe` uses `languages`, never `language`), `delay` (`minimal|low|medium|high|xhigh`).
- `gpt-live-transcribe` and `gpt-realtime-whisper` **do not support** `server_vad`/`semantic_vad`; the client must send `input_audio_buffer.commit` at the end of each turn. Other models can use server VAD (`turn_detection`), which only chunks audio in transcription sessions.
- Events: `input_audio_buffer.committed` (gives `item_id`, `previous_item_id`), `conversation.item.input_audio_transcription.delta` (`item_id`, `delta` text to append), `…completed` (`item_id`, full `transcript`, `usage`), `…failed`, `error`. Completion order across turns is **not guaranteed**; reconcile by `item_id`.
- No timestamps, confidence or speaker labels from `gpt-live-transcribe`. Billing for it is per audio minute.
- Browser alternatives exist (WebRTC or WebSocket with an ephemeral key from `POST /v1/realtime/client_secrets`); not used in v1, see Decision 2.

## Goals / Non-Goals

Goals: one authoritative draft and submission path; a pluggable recognizer contract; vendor credentials and vendor events never reach the browser. Non-goals: Whisper support, conversational realtime, TTS, agent tools, command classification, auto-send, new-session UI, changes to ordinary text shortcuts, timestamps or diarization.

## Decisions

1. **New `voice` core module with its own provider SDK.** Files `$voiceProvider_<id>.ts` in a mounted module or plugin default-export `types.voice.ProviderDefinition`; `$loader_voiceProvider.ts` validates them, records mounted-source ownership, rejects duplicate IDs, and isolates a bad declaration. A definition declares `id`, `label`, `destination` (`{ kind: "cloud" | "host", label }`), connection `fields` (same field types as Models: text/url/select/secret/number/boolean, no secret defaults), `models` (static list or `listModels`), per-model `capabilities` (`turnDetection: "client" | "server"`, `languages`, `keywords`, `prompt`, `delay`, `sampleRates`), `test(ctx, conn)` and `open(ctx, conn, session)` returning a `VoiceStream`. Connections live in a new `voice_connections` table with secrets in the existing secret store; projections are secret-free. Routes are `<provider>/<accountName>:<modelId>`. The public facade is minimal: `voice.providers`, `voice.list/get/create/update/remove/test`, `voice.resolveRoute`, `voice.effectiveRoute({ agentId })`. Everything else is in implementation namespaces, as in Models.
2. **Relay through the MauzCode server over one WebSocket.** Endpoint `$ws_voice_session.ts` (served via `procs.http.upgrade`: exact origin check, owner session, chat ownership and editability). Rationale: the key never leaves the server, adapters normalize vendor events, and future providers need no browser code. Accepted cost: one extra hop. An ephemeral-key browser→OpenAI path is rejected for v1 because it would put vendor protocol handling into the composer.
   - Client → server: text JSON `{type:"start", agentId, generation}` / `{type:"finish"}` / `{type:"cancel"}`; binary frames = mono PCM16 little-endian at the negotiated rate (24 kHz for OpenAI), 20–100 ms per frame, each prefixed by a 4-byte little-endian sequence number scoped to the generation. WebSocket already preserves order; the number exists only to detect client-side bugs (a resume opens a new socket, so frames of an old generation cannot arrive): a gap or repeat ends the session with `protocol`.
   - Server → client: `{type:"ready", sessionId, route, destination, sampleRate}`, `{type:"phrase", id, order, revision, text, final}`, `{type:"phraseFailed", id, order, reason}`, `{type:"completed"}`, `{type:"error", code, message}`. Closed `code` set: `unauthorized` (origin, owner or chat check failed), `readOnly` (edit access lost), `superseded` (another tab started dictation for this chat), `unconfigured` / `routeUnavailable`, `providerAuth`, `provider` (other sanitized vendor failure or disconnect), `timeout` (idle, finish or session limit; `message` says which), `backpressure` (frame or buffer bound exceeded), `protocol`. `message` is a short user-facing text without vendor payloads or key material.
   - Bounds: one active session per owner+chat (a new start cancels the old one), max frame 16 KiB, max buffered upstream 1 MiB, max session 5 min (enforced by the server: at the limit it stops accepting frames, commits and finalizes pending phrases, sends them and closes with `timeout`; the client shows the remaining time and keeps the draft unsent), idle 30 s without frames while listening, finish timeout 10 s. Exceeding a bound ends the session with a visible error. Edit access is checked at `start` and re-checked on every chat state change for the session's agent (archive, read-only, owner change); when it is lost the server cancels the provider stream and closes with `readOnly`. Audio is held only in memory; nothing is written to disk. Frames, transcripts and keys are never logged.
3. **Normalized session protocol at the adapter boundary.** `VoiceStream` = `append(pcm)`, `commit()`, `finish()`, `cancel()`, plus an event callback. Core is the only source of `order`: it numbers phrases in the order it calls `commit()` (its own VAD commits plus the finish commit), and the provider maps each commit acknowledgement to that order without computing its own. For future `turnDetection: "server"` models, core assigns `order` in the sequence the provider reports commits; providers never send `order` themselves. Core guarantees: each revision carries the complete phrase text, revisions are monotonically increasing, a final is emitted once, events after `cancel` or after the session's generation changed are dropped, `finish` resolves after every committed phrase is final/failed or rejects on timeout. A shared contract test suite runs against every provider with a fake transport.
4. **Segmentation on the MauzCode server.** Codex never commits manually: its transcription session omits `turn_detection` with `gpt-4o-mini-transcribe`, so OpenAI's default `server_vad` cuts phrases (its conversational mode uses `silence_duration_ms: 500`). `gpt-live-transcribe` does not support server VAD, so the cut must be ours. It runs in Voice SDK core, not in the browser and not in a provider: core applies an energy-based VAD to incoming PCM (speech after ≥ 500 ms of silence → `commit()`), forces `commit()` after 15 s of continuous speech, and commits on `finish`. Empty or silence-only buffers are not committed. A forced commit during speech is placed at the lowest-energy 20 ms window of the last 500 ms to avoid cutting a word; where the provider returns a split word, the client adapter joins adjacent phrases with a single space and does not try to repair words (accepted limitation, covered by a test with a synthetic 20 s utterance). Providers whose models declare `turnDetection: "server"` receive no core commits except on `finish`, and configure their own VAD. The browser only streams audio, so every client gets identical behavior and thresholds are tuned in one place.
5. **OpenAI Realtime adapter (`openai-realtime`).** Fields: `apiKey` (secret, required), `baseUrl` (default `https://api.openai.com/v1`), `organization`/`project` (optional). Model: only `gpt-live-transcribe` in v1 (live deltas, client turns, $0.017/min). `gpt-transcribe` ($0.0045/min, server VAD, text only after each turn) and `gpt-realtime-whisper` are deliberately not offered now; the `turnDetection` capability keeps the contract ready for them. Codex's `gpt-4o-mini-transcribe` is deprecated and not used; per-connection/chat options `languages`, `keywords`, `prompt`, `delay`. Open: `wss://…/v1/realtime?intent=transcription` with `Authorization: Bearer`, send `session.update` (`type: "transcription"`, PCM 24 kHz, `turn_detection: null`, `noise_reduction: near_field`), wait for `session.updated` (5 s timeout). `append` → `input_audio_buffer.append` (base64); `commit` → `input_audio_buffer.commit`. `languages` and `delay` are sent only when configured (default: not set, OpenAI defaults apply). Map `input_audio_buffer.committed` → bind its `item_id` to the oldest unacknowledged core commit (the commit's `order`); `previous_item_id` is checked only as a consistency assertion and a mismatch is a `provider` error; `…delta` → append to the phrase text and emit a revision; `…completed` → replace with `transcript`, emit final, add `usage` audio seconds to the in-memory session counter; `…failed` → `phraseFailed`; `error` / close → sanitized session error. Never send `response.create`, output audio or tools. `test` performs a short connect + `session.update` and closes without audio.
6. **Routing and preferences.** Setting `voice.defaultRoute` holds a route; the per-chat override is stored in the agent scratchpad as `voice.route` (written through `session.mutateScratchpad`, no migration); absence or removal of the key means inheriting the default. Resolve once at `start`; a preference change applies to the next session. No automatic fallback to another route.
7. **One capture controller for both views** (`useVoiceCapture`): states idle, connecting, listening, finalizing, paused, error; `getUserMedia` with echo cancellation/noise suppression, an `AudioWorklet` that downsamples to the negotiated rate and emits PCM16 frames. Before any microphone request the controller checks `window.isSecureContext`, `navigator.mediaDevices.getUserMedia` and `AudioWorklet`; if any is missing both controls stay visible but disabled with an explanation ("Microphone requires HTTPS or localhost" / "Browser does not support audio capture"), and no socket is opened. Tracks are stopped on pause, send, exit, navigation, access loss or socket close; resume starts a new generation and a new socket session. The editor adapter (implemented for both `CommandEditor` and `textarea`) tracks dictated spans anchored at the caret: a revision replaces only its own span, a manual edit detaches that span, clearing removes only still-owned spans. Attachments stay in `LiveComposer`; there is no second buffer or send route. Screen reader announcements go through one polite live region and are limited to state changes (listening, paused, finalizing, sent, error, moved to another tab, remaining time at 1 min and 10 s); interim and final phrase text is never announced automatically, the transcript is readable on demand in the panel.
8. **Finalization before submission.** Explicit send freezes input, calls `finish`, snapshots the draft and invokes the existing send/queue action once with its retry key; a request lock ignores repeated Enter/clicks. If finish fails, capture stops and visible text stays editable; nothing is sent. Acknowledged panel sends clear the submitted draft and leave the panel paused.

## Risks / Trade-offs

- Relay latency and bandwidth (≈ 48 KB/s per session at 24 kHz PCM16) → small frames, bounded buffers, backpressure error instead of silent drops.
- Out-of-order or late finals → order by commit chain, generations, finish timeout.
- Energy VAD misjudges noisy rooms → browser noise suppression, forced commit every 15 s, commit on finish; thresholds are core constants covered by tests.
- Cost surprise → destination and "metered" label before capture; `usage` audio seconds are counted in memory for the active session only and not persisted in v1 (no transcripts).
- Space conflicts with focused buttons in the panel → shortcuts are bound on the panel container and ignored when the event target is a button, input or editable element; every action also has a button.
- Two tabs on the same chat → one active session per owner+chat; the older session is cancelled and its tab shows "dictation moved to another tab".

## Migration Plan

New table and optional settings/chat metadata; absence means unconfigured or inherited. Existing chats, Models connections and the Whisper plugin need no conversion. Unconfigured installations show a "Configure voice" hint without requesting the microphone. Roll back by removing the entry points and the endpoint; the unused table does not affect chat. Implementation is verified with a fake OpenAI WebSocket server and synthetic PCM; no paid call is required.
