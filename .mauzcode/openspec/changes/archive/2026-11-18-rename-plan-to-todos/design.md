## Context

Todo tracking (today called "plan") lives in `agent.scratchpad.plan` (`{ version, title, tasks[], createdAt, updatedAt, pausedAt }`, tasks with `status`, `startedAt`, `activeSince`, `elapsedMs`, `completedAt`) and is mutated only through `session.mutateScratchpad` by `src/session/{plan,updatePlan,done,removePlan}.ts`. The native adapters `src/tools/planUpdate.ts` and `planDone.ts` wrap them. About 20 runtime files read `scratchpad.plan` directly (pause on stop/context guard, resume on user message/retry, team status, delegation, finishTask, metaSurface). The UI shows the plan only in the Meta panel (`core-ui/agent-meta.tsx`) via `/meta-settings`. Live updates flow through `events.refreshAgentMeta` → `ui.metaSection` on the shared SSE transport (`subscribeLive`). Above the composer, `LiveComposer` already stacks `GoalDock` and `QueueDock`. See proposal.md for motivation.

## Goals / Non-Goals

**Goals:** one consistent todo vocabulary with no aliases; a lossless data and preset migration; parallel active todos without breaking the single-active flows (delegation, finishTask, activation messages); a live read-only dock.

**Non-Goals:** user editing of todos in the dock; renaming planning mode; changing delegation semantics beyond the vocabulary; a dock for team members' todos (there is no Team section in the React Meta tab; after the Meta "Plan" section is removed, a person sees a child's todos in the dock of the child's own chat, opened from the chat-header subagents list, and agents read them through the `todos` field of `agent.team` members); stopping or pausing a single active todo (an active todo ends only through `todo_done` or by removing the list; there is no way back to pending).

## Decisions

1. **New `todo` namespace** (`src/todo/create.ts`, `update.ts`, `done.ts`, `remove.ts`, `$point_taskDone.ts`) instead of keeping the functions in `session`. The functions own a domain, not session persistence, and `todo.*` reads unambiguously in prompts and presets. Alternative `session.todos*`: rejected as a mix of two concepts in one namespace.
2. **Scratchpad key `todos`** (and `todoHistory`) with an unchanged inner shape (`version: 1`). Keeping the shape makes the migration a key move and keeps the timing logic as is. Alternative: a separate table. Rejected because it gives no benefit now and would split atomic scratchpad mutations.
3. **Parallel start through `update`**, not a new tool: a todo entry may carry `status: "active"`, accepted only for a todo that is pending or new in a revision of an existing list; it sets `status/startedAt/activeSince`. Any other value is rejected, and `status: "active"` on an already active todo is a no-op. When a list is created, the first todo is active and every todo marked `status: "active"` is active too; the rest are pending. The order rule (active and done before pending) is checked on creation as well as on revision, so `a, b, c(active)` is rejected in both cases. `done` auto-activates the first pending todo only when no active todo remains. This keeps the tool count at two, and sequential agents behave exactly as before. Alternative `todo_start` tool: rejected as extra surface for a rare case.
4. **Helpers for "all active"**: every place that used `tasks.find(status === 'active')` for pause/resume (`agent/stop.ts`, `stopContextGuard.ts`, `retryMember.ts`, `run.ts`, `acceptMessage.ts`, the messages POST route, `todo/remove.ts`) iterates over all active tasks. Decision: two runtime functions `todo.pause({ agent })` and `todo.resume({ agent })` own this logic (settle `elapsedMs` and clear `activeSince` for every active todo and set `pausedAt`; or clear `pausedAt` and restart `activeSince`). Both mutate through `session.mutateScratchpad`, are idempotent and emit the `todos` section. Consumers call them instead of editing `scratchpad.todos` inline; `todo.remove` settles timers in its own mutation. Four SQL scheduling guards read the pause directly from JSON and must move to the new key in the same change: `session/deliverInbound.ts` (`#>> '{plan,pausedAt}'`), `input/submit.ts`, `input/choiceBatch.ts` and `input/complete.ts` (`->'plan'->>'pausedAt'`). Missing one of them silently restarts stopped agents, so each gets a regression test. In `coreCatalogue.ts` the `todo` namespace is `standard` with the explicit patterns `todo.create`, `todo.update`, `todo.done`, `todo.remove`; `todo.pause` and `todo.resume` are not granted to Standard, so agents cannot drive the timers themselves (runtime callers keep normal internal access).
5. **Result shapes for several active todos.** `todo.done` adds `active: Array<{id,title,instructions}>` and keeps `next` (the todo auto-activated by this call or `null`) and `complete` (no active and no pending todos). `todo.create`/`todo.update` and the `todo_update` tool replace today's `active: string | null` (`planUpdate.ts`) with `active: string[]`. The `todo.taskDone` payload keeps `next` with the same meaning as in `done` and adds `active: string[]`, so handlers never have to guess which todo is "current". The delegation steer text ("Completed todo 2/5") is unchanged in meaning.
6. **Plan POST route**: `src/agent/$route_$id_plan_POST.ts` serves the old SSR/Meta edit form, which the React UI no longer uses (it exists only in tests). Because the dock is read-only and the Meta panel is removed, the route is deleted together with `planRoute.test.ts`, and the `plan_activation` producer goes with it. No `todo_activation` type is introduced. History rendering of `plan_activation` stays. `src/agent/humanResume.unit.test.ts` imports this route and must be rewritten against `todo.resume`.
7. **Read endpoint** `src/agent/$route_$id_todos_GET.ts`: same auth and ownership checks as the existing `/agent/:id/persistent-goal` GET, reusing `goal.surfaceAuthorize` (401 without a user session, 404 for unknown or archived agents, 403 for another owner); it returns a trimmed projection (no timing internals) with `Cache-Control: no-store`.
8. **Dock data flow**: `lib/todos.ts` `getTodos(agentId, signal)`; `TodoDock` fetches on mount and on `subscribeLive({ types: ['ui.metaSection'] })` events whose `agentId` matches and `section ∈ {todos, all}`, and in `resync`. `team` is deliberately ignored: it is emitted to the parent when a child's todos change, and the parent's own todos are not affected. No interval polling (unlike GoalDock). It reuses `queue-dock.css` tokens, adds `todo-dock.css`, uses the lucide icons `ListChecks`, `Circle`, `CircleDot` and `CircleCheck`, and has a `button` header with `aria-expanded`/`aria-controls`. It follows the Apple Design skill and respects reduced motion.
9. **Migrations**: `src/session/$migration_<ts>_plan_to_todos.ts` is boot-only, like `$migration_20330306120000_remove_legacy_scratchpad_results.ts`: it refuses to run while agents are loaded in `ctx.state.agent`, because `session.save` writes the whole in-memory scratchpad and would bring the legacy `plan` key back over `todos`. It updates `agents.scratchpad`, which is a `TEXT` column: it casts with `scratchpad::jsonb`, writes back with `::text`, and processes every row including archived agents. Each key moves separately and only when present: `plan` → `todos` only if `todos` is absent, `planHistory` → `todoHistory` only if `todoHistory` is absent; the old key is removed only after it was moved. No `null` keys are created (no `jsonb_build_object` over possibly missing keys). A row whose `todos` already exists keeps it and keeps `plan` for manual review, and the migration logs the count. A second run changes nothing. Rows with invalid JSON are skipped and counted, following `$migration_20330306120000_remove_legacy_scratchpad_results.ts`. `src/agentPreset/$migration_<ts>_todo_tools.ts` rewrites the grant strings `tools.planUpdate→tools.todoUpdate`, `tools.planDone→tools.todoDone`, `session.plan→todo.create`, `session.updatePlan→todo.update`, `session.done→todo.done`, `session.removePlan→todo.remove` in both `allow` and `deny` of factory presets, user presets and every layer of agent preset snapshots (`agents.preset_snapshot`). A wildcard that covered the old functions (`session.*`, `*`) gets `todo.create`, `todo.update`, `todo.done`, `todo.remove` added next to it in the same list, so an allow keeps access and a deny keeps blocking. Unchanged lists are not rewritten, and duplicates are not added, so the migration is idempotent. Rewriting snapshots is a deliberate exception to "snapshots freeze rules" (earlier preset migrations never touched snapshots); without it existing agents would lose todo tracking. A migration id is the whole file stem after `$migration_` (`procs/project/classify.ts`), so `20380106120000_plan_to_todos` and `20380106120000_todo_tools` are distinct ids and are applied in a deterministic `localeCompare` order (scratchpad move first, then grants); the two migrations are independent, so either order is correct. Migration ids must sort after the latest existing ones, e.g. `$migration_20380106120000_todo_tools.ts` and `$migration_20380106120000_plan_to_todos.ts`, otherwise a fresh database applies older preset migrations after them (`migrate.up` sorts by id with `localeCompare`). Before merging, re-check the ids against `main` and the open worktrees in `../wt/` (notably `show-provider-client-version`, which also touches `coreCatalogue.ts` and `sharedAgent/delegate.ts`) and bump them if another branch added a later or equal id. The scratchpad migration has a `down` that swaps the keys back under the same "only when present and target absent" rule. The preset migration is **forward-only** like the earlier preset migrations (no destructive `down`): its rollback is a restore from backup, see Migration Plan.
10. **Event names**: `refreshAgentMeta` section enum `plan` → `todos`; steer event `plan.completed` → `todos.completed`. It means that a delegated child finished its whole list (emitted by `finishTask`), so it uses the plural `todos.` prefix of the list; `todo.completed` was rejected because it reads as "one todo done" and collides in meaning with the per-step `task.completed`. The `LifecycleRow` label changes from "План завершён" to "Задачи завершены". `LifecycleRow` and `$route_v1_agents_$id_events_GET.ts` accept both the old and new names for display only.
11. **Prompt section id**: `$prompt_plans.md` keeps its file name and id `plans`, because `exclude_sections` in presets and snapshots may contain `plans`. Only its body, title and `requires` (`todo.create, todo.done, todo.update, todo.remove`) change, and `fullSystemPrompt.ts` checks `tools.todoUpdate`/`tools.todoDone`.
12. **Spec capability name**: the `native-plan-delegation` spec is replaced by a new `native-todo-delegation` spec. All its requirements move there (the delta removes them from the old spec and adds them to the new one), so after archiving the old spec is empty and is deleted. A rename keeps spec names consistent with the vocabulary; keeping the old name would leave "plan" in the one place readers look for the tool contract. Alternative: fold the tools into `agent-todos` — rejected because delegation and `finish_task` are not todo concepts.
13. **`todo.create` keeps `session.plan` semantics**: it replaces an existing list without archiving (callers that revise use `todo.update`) and keeps `deferPublication` for an unpublished child in a caller transaction, which `agent/publishGoalDelegation.ts` relies on.
14. **Remaining `plan` and `task` words.** "plan" stays only where it names something that is not renamed or must stay readable: planning mode (`/plan`, `planning.*`, `PlanModeBadge`, `docs/planning-mode.md`); the prompt section id and file `$prompt_plans.md` (decision 11); the legacy names inside migrations, their tests and history compatibility (`plan.completed`, `plan_activation` rendering); and the retired `native-plan-delegation` spec. Everything else uses "todo". "task" stays only in names that are not renamed: the `tasks` argument of `todo_update`, `delegate_task` and `todo.*` (renaming it would be another breaking change for every caller and stored prompt with no user-visible gain), the per-step team event `task.completed`, `finish_task`/`agent.finishTask`, and `todo.taskDone`. Prose, prompts, JSDoc and UI labels say "todo". The `rg` check in tasks 7.4 allows exactly these exceptions.

## Risks / Trade-offs

- [A running agent mid-turn during the upgrade still has `plan_update` in its in-memory tool list] → the migration runs at startup before workers resume, and the tool lists are rebuilt per request from the migrated presets.
- [A user preset grants `session.*` or denies an old name] → the preset migration rewrites `allow` and `deny` and adds `todo.*` names next to covering wildcards.
- [An agent excluded the `plans` prompt section] → the section id is kept.
- [Prompt snapshots, fixtures or the creator-prompt fixture still mention the old names] → the acceptance `rg` check covers `src/`, `frontend/src/` and `docs/`, and the fixtures are regenerated.
- [Parallel active todos confuse sequential agents] → the default behaviour is unchanged; parallel start happens only with an explicit `status: "active"`, and the tool description says to use it only for really parallel work.
- [External user plugins call `session.plan`] → this is a breaking change by decision; note it in the commit body. A check found no current hits in `plugins/` or the user plugin directory.
- [The model repeats `plan_update`/`plan_done` because they are in the transcript history] → `tools/call.ts` already answers an unknown tool with the list of available tools, so the next call uses `todo_update`/`todo_done`; a test covers this.
- [The preset migration cannot be undone automatically] → it is forward-only by design (see decision 9); take a database backup before the upgrade.

## Migration Plan

1. Deploy the code together with both migrations, which run on server start.
2. Verify: `SELECT count(*) FROM agents WHERE scratchpad::jsonb ? 'plan' OR scratchpad::jsonb ? 'planHistory'` returns 0 (apart from rows logged as conflicts), and no preset contains `tools.plan`.
3. Rollback of data: the scratchpad migration's `down` swaps `todos`/`todoHistory` back to `plan`/`planHistory`. The data shape is unchanged, so this is lossless.
4. Rollback of grants: the preset migration is forward-only. Restore `agent_presets` and `agents.preset_snapshot` from the backup taken before the upgrade, or reverse the rename by hand (`todo.*` → `session.*` names, `tools.todo*` → `tools.plan*`) and drop the `todo.*` entries the migration added next to wildcards.
