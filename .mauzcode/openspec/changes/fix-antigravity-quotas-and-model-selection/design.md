# Design

## Context

`provider/antigravity/usage.ts` currently reads `fetchAvailableModels`. `inventory.ts` and `mapUsage.ts` preserve a native ID, fraction and reset but no period. `QuotaMatrix` consequently renders a family remaining figure/range. `useQuotas` polls at 60 seconds while the provider's `usageRefreshMs` is 180 seconds; Settings takes a snapshot when the connection loads. This explains a source of lag, not proof that Google never updates. The live inventory was inspected; an authenticated **summary** was not obtained in this investigation because the existing request allow-list blocks it. Examples in tests must be synthetic, not presented as this user's quotas.

`catalog/listModels`, `inference/resolveRoute` and `inference/stream` use the connection's group metadata; filtering it by persisted member IDs makes simply hiding their switches unsafe. `ModelPicker.choose` treats live and draft differently; the current two-call live correction misses supported old levels and leaves a partial-failure window.

## Goals / Non-Goals

Use one authoritative snapshot per signed-in connection and one route-change rule for all entry points. Do not change catalogue discovery, widen general network access, add another login, send generations to measure quota, replace the SDK's generic variant dispatch, or add monthly data the service did not report. Do not migrate existing chat effort just because the software is upgraded.

## Decisions

1. **Read the summary through the fixed control API.** Extend `api.ts` and `request.ts` by exactly `retrieveUserQuotaSummary`; use the existing project resolver, Hub User-Agent, token management, no-redirect rule and bound transport. Decode `groups[].buckets[]` once. Recognize `gemini-5h`/`gemini-weekly` and `3p-5h`/`3p-weekly` with matching structured `window`; calculate used percent as `100 × (1 − remainingFraction)` and parse each reset independently. Keep other identifiable buckets, such as a model-only weekly limit, in additional details with their own identity; do not fold them into the general family. An extra bucket of an eligible family appears in that family card's details and in the collapsed indicator; an extra bucket of no eligible family appears only in the collapsed indicator. Conflicting identities/periods cannot win by array order. The bucket IDs and `window` values above are unverified for this account: a sanitized live summary read is the first implementation step and gates the parser and UI work; if the observed shape differs, the delta scenarios are corrected before task 1.1 continues (the allow-list entry is task 0.1, the read is task 0.2). Reject malformed envelopes as failed reads; a valid partial summary is a new observation with unknown missing values. Inferring windows from inventory, using translated names, or probing arbitrary endpoints would not establish those identities.

2. **Represent a family pool, not a fictitious model or account.** Carry a group-scoped observation (e.g. `scope: group`, structured group key and stable provider bucket ID) through `UsageReport`, connection normalization/cache, `frontendBridge.modelUsage` and the quotas API. Preserve existing ordinary account windows; build each eligible family's period projection from its structured buckets only. Derive card eligibility from enabled catalogue choices of the same connection, not bucket presence. Reuse the standard used-percent cells, thresholds, and missing-value renderer for each card. Settings, expanded/mobile sidebar and compact details consume the same measurements. Keep the accessible provider/account/family name and existing settings navigation; include the shared Claude/GPT label in details. A new account per family would misstate ownership and duplicate polling.

3. **Share freshness upstream and downstream.** Use a 60-second Antigravity freshness interval, consistent for sidebar and visible Settings with one in-flight probe per connection revision/sign-in. Subscribe both surfaces to the updated observation or invalidate/refetch the lightweight projection upon completion; don't leave one component's local snapshot stale for an extra interval. Keep the provider usage TTL shorter than the UI poll interval (for example 55 s against 60 s), or have a due poll request `refresh`, so a poll never receives an observation that expires just after it; otherwise a change could take two intervals to appear. Pause timers when hidden and check the age on return. Track last attempt separately from last successful observation and short-circuit overlapping timers/retries. On a transient failure retain the last good normalized snapshot as stale, including its original timestamp; with no success show unavailable. Never reuse it after sign-out, revoked access or account replacement. Don't globally bypass the usage cache or change another provider's cadence.

4. **Make the route change the unit of persistence.** In `agent.setModel` (behind the picker, both agent model POST routes and provider-scope fan-out), compare provider and model slug: a different model writes `auto`; the same slug on another connection keeps the effort if the target's cached catalogue lists it, otherwise `auto` — including a cold catalogue or one without reasoning levels; support is read cache-only, never by discovery. Model and `reasoning_effort` change in the same guarded write per agent, including fan-out targets. `onConnectionRenamed`, route migrations and `session/save` keep `reasoning_effort` untouched. Synchronize the live pair before unpark or inference; retain the previous pair for guarded rollback and publish committed metadata/events consistently. Coordinate manual effort edits with route changes so a stale write cannot overwrite a later selection. Remove the picker's follow-up effort mutation; read back the committed state. Keep `setReasoningEffort` and the effort POST for explicit choices (correct the old retention documentation). Draft `choose` emits `(route, 'auto')` on switch; `lib/models.ts` distinguishes true replacement from restoration/alias normalization. Submit the resulting pair through the existing new-session flow; do not reset every time draft configuration is fetched.

5. **Convert member disables only when membership is known.** Put the group rule in one shared availability function used by `listModels`, `selectable`, `assertModelEnabled`, native search and Settings, so unconverted stored flags already yield group-level availability. Persist the conversion after each successful catalogue refresh (same write as the catalogue) and in a startup pass over connections with trustworthy catalogues; never from a cache-only read. Normalize the connection's disabled-ID set using validated, nonempty group metadata *before* applying owner filters. For each confirmed group: keep/add the group ID if explicitly off or all its eligible members were off; otherwise leave it on. Remove only that group's proven legacy member flags. Write only changed data, guarded by connection/catalogue revision, retrying against the latest state if needed. Defer unproven IDs until valid membership is available; never group by string suffix. Prevent new per-member disables for known Antigravity groups in `models.catalog.setModelEnabled` itself (so the `/models/api` action and runtime callers are covered), failing `VALIDATION` with the group ID and no write; keep standalone and other-provider behavior intact. Settings saves the group ID only. Enabling a group with a trustworthy mapping removes that group's proven member disables in the same guarded write, so a fully disabled legacy group comes back at once and a later conversion cannot turn it off again; without a mapping only the group ID changes. The SDK variant rule gains a provider-declared group-level availability flag (Antigravity sets it), so `models.stream` stops dropping levels for legacy member flags while other variant providers keep per-member behaviour. Continue passing the exact native member ID for the selected effort and reject direct legacy routes absent from the catalogue. Generic SDK handling for providers that still support member disables does not change.

## Risks / Trade-offs

- **Upstream bucket variations or missing family:** show unknowns and independent extras rather than silently merging or reusing obsolete values. The live acceptance step checks only the reported groups and fields.
- **Misreading 100%:** fraction 1 means 0% *used*; an exhausted window means 100% used, and an absent window means `—`. Verify both endpoints and partial snapshots on both surfaces.
- **Repeated polls or stale account leakage:** share in-flight reads, guard against late responses after sign-in/revision changes, and verify one provider call per due interval across both consumers.
- **Old disable flags are not reversible from group state alone:** keep conversion scoped and compare revisions; do not guess when catalogue evidence is unavailable.

## Migration Plan

0. Before any parser or UI work, make one authorized, non-generating summary read and record its sanitized shape (group/bucket IDs, `window`, fraction, reset). Stop and revise the specs if it differs from the assumed IDs. The read is an outward action on the owner's account and runs only after the owner's explicit approval. If it fails or is not approved, quota work (tasks 1.1–2.3 and 5.2) waits; group availability and effort reset (sections 3 and 4) have no dependency on it and may be implemented and verified, but the change cannot be closed with quota acceptance unverified unless the owner explicitly splits the quota part into a separate change.
1. Land the reader and additive grouped quota contract before switching UI consumers; invalidate pre-summary usage snapshots rather than treating them as period observations. Keep catalogue data available for model routing.
2. Roll out grouped availability normalization and the settings UI together, applying the idempotent conversion per connection with a valid catalogue. For an operational rollback that must restore historical effort disables, use an authorized pre-upgrade backup of the affected connection settings; the normalized group switch alone cannot reconstruct the old selections.
3. Ship the atomic route reset and draft changes together. Verify synthetic cases in isolation and then one authorized live summary read on the configured connection. Record only sanitized group/bucket identity, period, percent and reset (or absence); no raw account data or generation. A failed check or missing window is reported as such, not substituted from other accounts.
