# Подготовить OpenSpec change

Общайся с пользователем на русском языке.

Результат — согласованное описание изменения с проверяемыми задачами, не код. Прочитай актуальный `AGENTS.md` целевого checkout и инструкцию плагина OpenSpec. Работай через `openspec.run`, не через `openspec` в shell. Файлы — под `.mauzcode/openspec/` выбранного проекта.

## Выбрать цель до записи

- Запроси свежий список открытых изменений (`list --json`). Если ID не указан, покажи форму выбора: **ID + короткое описание** из proposal каждого открытого change и отдельный пункт **«Создать новый change»**. При длинном списке используй `grid`. Не угадывай по ветке или истории и не выбирай автоматически, даже если change один. Дождись ответа.
- Если открытых нет, скажи об этом и предложи подтвердить создание нового. Ошибка чтения списка — не пустой список. Отмена выбора — остановка без изменений.
- Явный ID существующего change проверь по списку. Если назван неизвестный или архивный ID, объясни это и уточни намерение; не подменяй цель и не возобновляй архивный change. Явная просьба **создать новый** с заданным ID — это не попытка открыть существующий: проверь отсутствие коллизии, включая архив.

## Согласовать и описать

1. Прочитай относящийся к идее код, действующие спеки и конфигурацию. Для открытого change сначала прочитай его артефакты. Определи, что уже работает и какой наблюдаемый результат должен измениться. Не проси пользователя выяснять то, что можно проверить в проекте.
2. Задавай вопросы только о выборе, который влияет на сценарий, объём, совместимость или критерий готовности. Если есть содержательные варианты, объясни их отличия и предложи один. Пока границы не согласованы, не создавай артефакты. Если пользователь просит сначала поработать в режиме планирования, соблюдай порядок согласования плана.
3. Для нового change после согласования создай его через `new change <id>`; для существующего сохрани относящиеся к делу решения и чужие правки. Проверь действующие capability ID, чтобы не создать дубль. Подготовь `proposal`, дельты `specs`, `design`, `tasks` по зависимостям: непосредственно перед записью **каждого** артефакта запроси `instructions <артефакт> --change <id>` и следуй правилам проекта, в том числе языку артефактов. Свяжи сценарии с наблюдаемым поведением и проверяемыми задачами.
4. После правок выполни `validate <id> --strict` по правилам плагина; по мере заполнения устраняй диагностику, перед сдачей добейся чистого результата. Кратко сообщи ID, что согласовано и результат проверки. Если проверка недоступна или не прошла, не называй спеку готовой.

**Стоп:** не реализуй задачи, не отмечай их выполненными, не создавай коммит и не архивируй change.
