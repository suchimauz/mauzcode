# Сделать Git-коммит

Общайся с пользователем на русском языке.

Результат — один проверенный локальный коммит в выбранном checkout. «Коммит спеки» может предшествовать реализации: это просьба сохранить документы, а не выполнить задачи или закрыть change. Прочитай `AGENTS.md` проекта, особенно правила сообщений и OpenSpec-ссылок; если затронут OpenSpec, прочитай актуальную инструкцию его плагина.

## Выбрать область

- Если ID change не передан, запроси свежий список открытых изменений через `openspec.run` (`list --json`) и спроси пользователя. Покажи в форме ID и короткое описание из proposal каждого change плюс **«Без привязки к OpenSpec»**. Не выбирай автоматически даже при одном change; для большого списка используй `grid`. При пустом списке прямо скажи об этом и предложи вариант без привязки. Ошибка получения списка — не пустой список. Отмена — остановка.
- Если указан неизвестный или уже архивный ID вместо открытого, объясни это и уточни, что именно сохранить; не подставляй другой ID. Если человек специально просит коммит уже выполненной архивации, проверь связь по diff и документам в архиве, не открывай change заново. Не выдумывай ссылки. Если выбран вариант без привязки, но в diff есть явно относящиеся к change файлы, уточни область, а не добавляй их молча.

## Собрать коммит и показать его пользователю

1. Проверь корень, ветку, `git status`, обычный и staged diff. Найди относящиеся к просьбе изменения, включая новые файлы. Не выводи секреты, не включай локальные настройки, временные файлы и чужую работу. Если в одном файле несколько задач, раздели только однозначно относящиеся к коммиту фрагменты; при сомнении спроси. Если чужие изменения уже в индексе и их нельзя безопасно обойти, остановись: не сбрасывай индекс и не включай их. Не используй `git add -A` вслепую. Если сохранять нечего, сообщи об этом и не создавай пустой коммит.
2. Проверь именно то, что будет закоммичено. Для OpenSpec следуй правилам плагина: строгая проверка каждого затронутого открытого change; при правках основных `specs/`, в том числе архивных дельт, уже перенесённых туда, — полная `openspec.validateAll({ dir })`. Невыполненные проверки обозначь, не выдавай их за пройденные. Не подмешивай исправления в «коммит спеки» без согласования.
3. Подготовь сообщение по актуальному `AGENTS.md`: краткий английский `type(scope): description`; для чистой спеки — `spec(openspec):`, для реализации — тип по основному эффекту. Укажи подтверждённые `OpenSpec-Change`, `OpenSpec-Spec`, `OpenSpec-Tasks` применительно к фактическому diff; не выдумывай задачи ради заполнения блока. Для обычного коммита без связи не добавляй OpenSpec-ссылок.
4. Покажи ветку, точный состав коммита, сообщение и статус проверок. Получи предусмотренное подтверждение **этого коммита**. Перед записью ещё раз сверь staged diff с согласованным; если состав изменился — не используй старое подтверждение. После коммита проверь SHA, файлы и остаток рабочего дерева, кратко сообщи результат.

**Стоп:** не меняй статус change, не отмечай задачи, не мержи, не архивируй, не пушь и не переписывай историю. Не начинай следующий коммит автоматически.
