# Codex response controls: rollout and offline rollback

**Roll forward:** Back up the database and verify restoration on an isolated clone. Apply the additive account-generation, publication-order and chat-consent migrations before deploying readers/writers. No backfill: never infer the owner of old catalogues or checkpoints. Deploy validation, discovery, cache publication and dispatch together; expose the picker last. A cache-only read never needs a refresh. A normal successful listing under verified credentials can publish controls. Pre-existing default-only chats can keep working without discovery. Ordinary token renewal is not an account switch.

**Before a downgrade:** Hide/disable picker writes, stop ingress, refresh timers, queues and every process or supervisor that can read/write this database. Drain/cancel in-flight model requests and wait for their transactions to finish. Keep both binaries offline; an idle worker or a table lock is not a writer barrier. Confirm the database identity, exclusive maintenance access, tested backup and intended old build. Perform the following on a disposable restored copy first. Do not point automated tests at working storage.

1. With all writers stopped, run `psql -X -v ON_ERROR_STOP=1 --dbname="$EXPLICIT_OFFLINE_DATABASE_URL" --file=maintenance/codex-model-controls/rollback.sql` using an explicitly selected offline database. The script takes non-waiting table locks, does not contact a provider, and never edits messages/events or prints checkpoint bodies. It does not drop additive tables or reset billing preferences to another fast tier.
2. A **blocked chat ID** means the transaction failed without persistent changes. Do not start an old reader. Restore complete compatible history from a verified backup (or stay on the new version and start a new chat). Do not strip signatures, shorten a frontier, relabel an account or treat ciphertext as portable. The conservative offline verifier reports rather than guessing about canonical checkpoints, inherited history, metadata/attachments it cannot hash, missing or changed history. Include archived and hidden sessions in recovery. A newly created chat does not make an unsafe stored session safe to downgrade.
3. On success, incompatible Codex snapshots are cold, explicit chat `max` becomes `auto`, and unsafe sleep generations whose canonical source was proved available cannot be selected. Other providers, ordinary effort settings, portable generations and dormant consent rows are left alone. Run the cleanup a second time: it is idempotent. Rehearse a default request on the old reader using **mock transport**. Restore the backup if any check fails; only then, with explicit operational approval, repeat the verified procedure on the target and restart old readers. Re-enable ingress last. No provider refresh is required for cleanup.

**Re-upgrade after running the old binary:** Old OAuth writers cannot maintain generation or revision fences. Do not reuse pre-downgrade account bindings, catalogues or consent as proof of present identity. With both versions quiesced, require a fresh login/binding for every Codex connection and invalidate prior-generation consent before exposing overrides; preserve no opaque state across that boundary. Never manufacture a binding from the old account label. Re-enable discovery and the picker last.

**Regression rehearsal:** From a checkout with the pre-change commit `18e341837f4ee6a55296838a471c2cc800979b4d` available, `bun test ./maintenance/codex-model-controls/rollback.it.test.ts` uses isolated test Postgres, executes the SQL twice, then projects and sends from the prior reader to a mock account B. A missing-history fixture demonstrates the blocking path.
