# Desktop pilot build and distribution runbook

**Public distribution disabled.** Nothing here approves repository creation, a publish, a stable release, or use of signing credentials. `.github/workflows/desktop-pilot.yml` checks source on the three OS families, with read-only access and no uploads. Native release builds run only in a separately authorized, protected source build environment. Do not put the source checkout, CI, private configuration or tokens in the proposed public release-only repository. GitHub generates public tag archives from that repository's tree. A prerelease tag is public, not access control.

## Inputs and identity

Keep npm name `mauzcode-desktop`, Electron product `MauzCode`, app ID `dev.mauzcodecode.desktop`, partition/profile paths and NSIS installation scope. Legacy version is 0.1.0. Use monotonically increasing versions `X.Y.Z-pilot.N` (current source version is not a published release). The legacy wrapper requires one manual install of the first reviewed pilot over the existing app; do not uninstall, clear profile data or move the profile. Confirm saved address and valid same-origin login survive. A new user gets the connection screen. Build N and N+1 from separately reviewed revisions, with compatible OS identities and the same authenticated feed trust root.

An owner must independently verify the dedicated release repository, pilot channel, release-signing Ed25519 public SPKI fingerprint and Windows Authenticode signer CN out of band. Materialize exactly these public fields in `desktop/update-pin.json` before packaging: `repository` (owner/repo), `channel` (`pilot`), `publicKey` (PEM PUBLIC KEY), `publisherName`. No fallback/test pin, environment-selected feed, server address or release token. Missing or malformed pin blocks builds; validation alone does not prove ownership. Compare the ASAR pin with the separately approved copy. Keep private signing keys outside checkout, upload directory and application.

## On controlled native build hosts

The `native_build` dispatch input defaults to **false**. Before enabling it, configure a required human reviewer for the `desktop-pilot-build` environment and use dedicated, trusted self-hosted runners labelled `desktop-pilot-windows-x64`, `desktop-pilot-macos`, `desktop-pilot-linux-x64`. They need Bun, Node, the platform toolchain and a host-local `PILOT_PIN_FILE` (only the four reviewed public fields). Provision signing identities in the protected native key store, and obtain separate approval for Apple notarization including submitting the app and both DMGs. No signing or release credentials go to pull-request jobs. Native builds are permitted only from the default branch; they leave output in `dist/` for private inspection on the controlled runners, not in public CI artifacts. Do not dispatch this workflow as part of local apply.

From `desktop/`, install the locked toolchain (`bun install --frozen-lockfile`, only with explicit installation approval) and run `bun test` with the repository-root locked DOM test dependencies available. Run `bun run build:win` on Windows x64 with the approved Authenticode signer, `bun run build:mac` on a Mac with Developer ID Application and working notarization credentials, and `bun run build:linux` on Linux x64. Commands force `--publish never`; do not switch to a publish mode. Builder creates x64 NSIS, Intel and arm64 DMGs **and ZIPs**, and x64 AppImage. The Windows Electron cache can be primed using `bun run prefetch:win` under the same dependency/download authorization. Never disable signature enforcement, Gatekeeper, download quarantine or Chromium sandboxing.

* Windows: check `Get-AuthenticodeSignature` status Valid and signer CN on installer and installed executable, PE x64 architecture and the NSIS upgrade path. Signing for an internal pilot is not proof of SmartScreen reputation or approval for broad stable distribution.
* macOS: the app uses hardened runtime, JIT and audio-input entitlement, microphone usage description and native OS consent (no camera entitlement). With **separate Apple submission approval**, set `NOTARY_PROFILE` to the approved Keychain profile, run `bash tools/verify-mac.sh` from `desktop/` to verify app/DMG, submit and staple each final signed DMG. Inspect both apps *inside the shipped DMGs and extracted ZIPs* using `lipo -archs`, `codesign -dv --verbose=4`, `codesign --verify --deep --strict`, `spctl --assess --type execute`, `xcrun stapler validate`. Match Team ID, Developer ID, entitlement and exact architecture across containers and N/N+1. Do not mutate the app after constructing ZIP. Public quarantined first launch is a later, independent gate.
* Linux: verify architecture using `file`/`readelf` on the actual executable in the extracted AppImage. Install the AppImage in a writable user-controlled location, record execute permission, distro, FUSE support, notification daemon and tray availability. Test with and without a tray; do not recommend sandbox bypasses.
* Microphone access is separate at the app/origin and OS levels. Test allow, deny, revoke while recording, and OS privacy settings (macOS Privacy & Security / Microphone, Windows Microphone privacy settings, Linux audio/session/portal configuration). Restart if the OS requires it. Revoking app permission must stop current capture; switching servers must not transfer consent.

## Inventory and public handoff (manual gates)

1. Inspect the final native packages, not only source or builder output. Extract/install into clean isolated workspaces. For **every** embedded `resources/app.asar`, run `node tools/check-asar.cjs PATH_TO_ASAR REVIEWED_PIN`. Record first-party inventory and audit dependency files/unpacked resources against locked production dependencies (electron-updater and its transitives); inspect non-ASAR resources too. No server runtime, source checkout, tests, build scripts, .env, credentials, logs, profile, private host or internal URL. Review literal URLs in first-party code/config and release notes: only public infrastructure, literals required by web standards, or clearly non-resolving examples; no actual collaboration endpoint. This inventory checker cannot discover secrets inside arbitrary binaries; human artifact review remains mandatory.
2. Stage only the six final installers/archives, outside `dist`. Generate a **private** inventory JSON of four update files as `[{"filename":...,"platform":...,"arch":...}]`: NSIS (`win32/x64`), both ZIPs (`darwin/x64`, `darwin/arm64`), AppImage (`linux/x64`). In the separate authorized signing environment, run `node tools/sign-release.cjs VERSION pilot STAGE PRIVATE_INVENTORY PROTECTED_KEY_FILE`. The two DMGs are OS-signed/notarized fresh installs; ZIPs are macOS update inputs. Run `node tools/verify-release.cjs VERSION STAGE REVIEWED_PIN_JSON` to verify `desktop-manifest.json` signature using the reviewed public key and rehash actual staged update bytes. No unauthenticated YAML as update authority. Keep per-asset SHA-256 receipts including both final stapled DMGs.
3. Write exactly the reviewed public text exported as `notes` by `tools/inventory.cjs` into `STAGE/NOTES.txt`. Run `bun run inventory STAGE VERSION REVIEWED_PIN_JSON`; privately retain the resulting size/hash list. Never upload a glob from dist. Reject extras, debug files, private inventory, keys, source, workflow and builder metadata. Record a public-safe review of every artifact and notes; missing native artifacts or signatures = no publication. The dry-run fixture checks shape/notes, not real installer safety.
4. Stop. Only after explicit human authorization for repository creation **and separate authorization for the exact release upload** may an operator use short-lived, narrowly scoped contents-write access to the release-only repo (no source repo access or client-side credentials). Use prerelease tags `vX.Y.Z-pilot.N`; never mark latest/stable. Verify anonymous HTTPS release/asset reads with no server cookies or token, signature/digests and stable exclusion for both N and N+1. No automated publishing workflow is provided. Record installed acceptance in [PILOT.md](PILOT.md).

## Failure, recovery, stable

If discovery, signatures, network or OS checks fail, leave the running installation and profile untouched; do not offer a fallback feed or unsigned installer. If an authentic release is faulty, obtain authorization to withdraw the offer and issue a higher corrected signed pilot; never auto-downgrade. For assisted recovery retain the known-good signed installer and a private owner-managed profile backup; do not delete or upload the user's profile. Stable requires a separate human decision with complete platform evidence, support/recovery ownership and Windows signing/reputation distribution review. No stable release is authorized here.
